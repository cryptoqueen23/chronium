# Investigator Acceptance Test — Chronium Mind

A permanent, rerunnable benchmark measuring whether Chronium actually reduces
an investigator's manual workload on a realistic municipal-records corpus —
not whether unit tests pass. This is a different kind of test than
`docs/INVESTIGATION_WORKSPACE_PLAN.md`'s phase-by-phase regressions: those
prove each feature enforces its own rules correctly in isolation; this one
puts a simulated three-person investigation team through a full, cluttered,
adversarial corpus and measures the *outcome* — what got found, what got
missed, how much manual work remained, and where the tool actively created
risk instead of reducing it.

**Run this again after any future phase** (`node
scripts/run-acceptance-test.mjs` against a running `wrangler dev`) and
compare the new result file's numbers against the "Benchmark History" table
at the bottom of this document. The corpus and the answer key
(`data/acceptance-test-corpus/`) are permanent fixtures — never regenerate
or discard them casually; they are the fixed ruler every future phase gets
measured against.

## Methodology (read this before the numbers)

`data/acceptance-test-corpus/manifest.json` is a **test oracle / answer key
only**. Chronium itself never had access to it — the harness
(`scripts/run-acceptance-test.mjs`) drives the real, unmodified production
UI at commit `83cc986` exactly as a human would: real file uploads through
the real dialog, real clicks on real buttons, real typed questions. Every
"investigator decision" in the script (confirm a candidate, reject a
candidate, write a claim) is made by reading the on-screen passage/snippet
Chronium actually renders, not by consulting the manifest. The manifest is
read exactly once, at the very end, purely to grade what already happened —
precision, recall, and the identity-safety scoring below all come from
comparing recorded actions against it after the fact.

**Production code was not modified for this test.** Three real bugs were
found in the process and are recorded below with severity/repro/expected/
actual/impact — none were fixed, per instruction. Everything added by this
work is confined to `data/acceptance-test-corpus/`,
`scripts/run-acceptance-test.mjs`, `scripts/build-acceptance-corpus.mjs`,
and this document.

## The corpus, audited

**Larkspur Falls, TX** — a fictional municipality, deliberately not
Copperas Cove (the project's real proof corpus) so the two never mix. 222
documents, generated by `scripts/build-acceptance-corpus.mjs` with a
deterministic seed (byte-identical on regeneration, so the corpus itself is
reproducible even though it should never actually need regenerating):

| | |
|---|---|
| Total documents | 222 (187 `.txt`, 31 `.csv`, 2 `.pdf`, 1 `.docx`, 1 `.xlsx`) |
| Hand-authored "signal" documents | ~27 |
| Templated "background noise" documents | 190 (50 unrelated council minutes, 40 agendas, 30 unrelated LFEDC minutes, 30 budget CSVs, 20 vendor invoices, 10 ordinances, 10 press releases — spread 2022–2025) |
| Intentionally corrupted/malformed files | 5 (fake PDF, truncated PDF, fake XLSX, fake DOCX, zero-byte TXT) |
| Exact-duplicate documents (by SHA-256) | 0 — verified directly; the corpus is byte-unique by design (see "Corpus limitation" below) |
| The money trail | 9 documents: EDC → board vote → council ratification → grant agreement → invoice → payment, spread non-adjacently on purpose |
| Deliberate contradictions | 3: vote outcome (4-1 vs. "unanimous"), paid-vs-invoiced amount ($185,000 vs. $178,500, a real unexplained $6,500 gap), meeting date (March 12 vs. a news brief's "April meeting") |
| Person↔org↔government-body chains | 4 people (Raymond Payne, Victor Holt, Sheena Tanner, Diane Castellano), each 2–3 documents |
| Identity-ambiguity set | 4 full-name docs (2 Marc Payne, 2 Raymond Payne), 2 alias docs ("Ray Payne"), 6 bare-surname docs that should read AMBIGUOUS, 2 of which are genuinely undecidable from text alone even by a human, 1 "mistaken identity fuel" letter falsely implying a "Councilman Payne" |
| Watchlist-friendly terms | LFEDC, Riverwalk Redevelopment Fund, Ordinance No. 2024-31, Holt Construction |

**Verdict on the corpus itself: it is well-designed and genuinely tests the
problems that matter.** The money trail is realistically non-adjacent (not
handed to the investigator pre-sorted), the identity-ambiguity set correctly
distinguishes "should be ambiguous" from "genuinely undecidable even by a
human," and the noise-to-signal ratio (190:27) is realistic. It earns its
place as a permanent benchmark, exactly as requested.

**One real corpus limitation, not fixed (regenerating would violate "don't
discard this because it could be prettier"):** the corpus has zero
exact-duplicate documents — every file is byte-unique by design, so
cross-filename/cross-folder duplicate detection (the same document appearing
twice under different names) can't be exercised from the corpus alone. This
test substituted a full re-ingestion of the identical 222 files as the
closest real equivalent (see Bulk Ingestion below). A worthwhile future
addition to the corpus — not done here — would be 2–3 documents saved twice
under different filenames.

## EXECUTIVE VERDICT

**CONDITIONAL GO.** The evidence model itself is sound: nothing in this test
found Chronium inventing a relationship, a finding, or a confirmed identity
that wasn't explicitly investigator-approved. Deduplication, failure
recovery, review-queue speed, and the core money-trail/contradiction
mechanics all worked well. But two HIGH-severity gaps mean Chronium is only
safe to use today with specific investigator discipline the tool does not
yet enforce or even hint at: (1) its primary conversational search — Ask
Sources — silently returns zero results for essentially any full-sentence
question, including all 12 of this test's own example questions, while
short keyword phrases work reliably; (2) a bare-surname candidate (like
"Payne") renders as an ordinary, confident single-option "Confirm" button —
visually indistinguishable from a genuine strong match — whenever only one
same-surname person happens to be registered yet, which is the normal state
at the start of any real investigation. Both are documented in detail below
with reproduction steps. Neither was fixed, per instruction.

## WHAT CHRONIUM CAN DO TODAY

- Bulk-ingest hundreds of real documents (txt/csv/pdf/docx/xlsx) through one
  dialog, fast (222 documents in 3.5s), with zero manual intervention.
- Correctly deduplicate re-ingested identical content by SHA-256, at full
  corpus scale, without re-processing.
- Detect possible-subject candidates against a registered entity roster and
  correctly force AMBIGUOUS — never a silent auto-pick — the moment two
  same-surname people are BOTH registered (verified 6/6 exact match against
  the corpus's own designed ambiguous-document set).
- Confirm a candidate through the real production APIs (`createEvidenceItem`
  → `createEntityMention`), preserving exact quoted text, with every Phase
  1–3 integrity rule intact.
- Find the entire real money trail (6/6 official chain documents, plus all 6
  documents behind all 3 known contradictions) via three short keyword
  searches — zero manual filesystem browsing needed, once you know to
  search with short phrases rather than questions.
- Keep two supporting/contradicting evidence items visible on the same
  claim simultaneously — never collapsing to one verdict.
- Never auto-create a relationship or finding from two people merely
  co-occurring in one document, even after both are confirmed as candidates.
- Triage a queue item fast — 383ms and one click ("Mark reviewed") for the
  large majority of records that have nothing to review, with the app
  auto-advancing to the next item.
- Give three different named investigators a shared, timestamped,
  attributed audit trail of every meaningful action.

## WHAT IT CANNOT DO TODAY

- Answer a real, naturally-phrased investigator question. Every one of this
  test's 12 example Ask Sources questions ("Show me every record mentioning
  Raymond Payne," "Did Raymond Payne serve on City Council?" etc.) returned
  zero results — not a timeout, a genuine, fast, wrong answer. See Bug #3.
- Warn an investigator that a single-option "Confirm as X" button is a weak,
  context-free surname match riding on an incomplete entity roster, rather
  than a strong match. See Bug #1.
- Re-scan already-ingested documents after a new entity is registered —
  there is no such control anywhere in the UI. See Bug #2.
- Answer any "what's left to do" / gap-awareness question in natural
  language (same root cause as the search bug above) — this has to be
  manually reassembled from several separate filtered views.
- Suggest, surface, or pre-fill an organization or government-body
  connection from a confirmed mention — every such link is entirely manual.
- Distinguish, anywhere in its own UI, "mark irrelevant" from any other
  action — the brief's review-action list included it, but no such control
  exists; "Flag" and "Mark reviewed" are the only two terminal-ish actions
  available besides confirming/rejecting a candidate.

## WHERE IT SAVED INVESTIGATOR TIME

- **Bulk ingestion**: 222 real documents, three file types, in 3.5 seconds,
  with zero manual sorting.
- **Deduplication**: a second full pass of the same 222 documents correctly
  recognized all 222 as duplicates in 1.3 seconds — no wasted review-queue
  clutter from re-ingesting the same source twice.
- **Money-trail discovery**: three keyword searches, under 2 seconds of
  total search time, surfaced literally every document in the official
  6-document chain and every document behind all 3 known contradictions —
  what would otherwise mean opening and reading through a meaningful
  fraction of 222 documents by hand.
- **Review-queue triage**: 383ms and a single click per record for the ~92%
  of records (23/25 sampled) that are pure noise with nothing to review —
  the app's own auto-advance-to-next-item behavior removed an entire
  navigation step per record.
- **Confirmed candidates → real evidence, in one click**: turning a
  detected "Ray Payne" mention into a real, quotedName-preserving
  `entityMention` took one button click, not a manual excerpt-and-link
  workflow.

## WHERE IT STILL CREATES MANUAL WORK

- **Every organization/government-body connection is fully manual.**
  Representing "Raymond Payne is on the LFEDC board, which reports to
  Council" required creating 2 entities and 1 relationship by hand — nothing
  suggests this from the mention that already exists.
- **Ask Sources' natural-language failure pushes ALL discovery work onto
  manually-composed short keyword searches.** An investigator who doesn't
  already know to avoid full sentences gets zero results and no hint why.
- **Re-scanning for new identities after mid-case discovery is entirely
  manual** (and not even UI-exposed — see Bug #2) — in a real investigation,
  discovering a second same-surname person mid-case is the norm, not the
  exception.
- **Cross-referencing the audit trail requires manual lookups.** Every
  `reviewHistory` entry is a raw ID with no rendered label — Investigator C
  could tell WHAT KIND of action happened and WHO did it, but had to
  separately open the Review Queue or Subjects tab to find out what any
  given ID actually referred to.
- **Gap-awareness is scattered across several separate filtered views**,
  each answering one narrow question (status counts, an "ambiguous" filter,
  a "failed" filter), with no single "here's what's left" summary and no
  natural-language path to any of it.

## IDENTITY-RESOLUTION RESULTS

This is the project's namesake test, run through automated bulk detection
for the first time (previously only exercised via manual, one-at-a-time
entry in Phases 1–4).

**Phase A — realistic starting state (only Raymond Payne registered):**
18 "Payne" candidate occurrences surfaced across the corpus. Reading each
one's actual on-screen snippet (not the manifest), the simulated
investigator confirmed 10, rejected 7, and left 1 genuinely undecidable.
Zero false identities were actually created — but only because the test
methodology insisted on reading every snippet. **The system itself offered
no protection here**: a bare "Payne" match with only Raymond registered
renders as an ordinary, confident "Confirm as Raymond Payne" button,
visually identical to a real strong match, regardless of whether the
passage is actually about him. This is Bug #1 below.

**Phase B — complete roster (Marc Payne registered mid-case, matching a
realistic investigative discovery):** the exact 6 bare-surname documents the
corpus's own design flags as "should read AMBIGUOUS once both people are
known" were individually re-scanned via the same production function the
ingestion pipeline itself uses (`scanRecordForReview` — there is no UI path
to do this, see Bug #2). **Result: 6 of 6 correctly reclassified AMBIGUOUS**,
an exact match against the manifest's ground truth, with both Marc Payne and
Raymond Payne rendered as separate, independently-labeled options — never
one pre-picked. This confirms the underlying detection algorithm
(`findSubjectCandidates` in `public/ingestionReview.js`) is fully correct
*once given a complete entity roster*. The gap is entirely about the
in-between state — the normal, everyday state of a real investigation where
not everyone relevant has been registered yet — and the total absence of
any mechanism to revisit it.

**Co-occurrence**: Raymond Payne and Sheena Tanner both appear in the same
board-minutes document. Both were confirmed as separate candidates. Zero
relationships were auto-created between them, before or after confirmation
— the only relationship that exists in this investigation is the one
manually created in the cross-document test, and it points to LFEDC, not
Sheena.

**Claim test** — created the deliberately incorrect claim "Raymond Payne
served on the Larkspur Falls City Council," directly informed by the
corpus's own built-in "mistaken identity fuel" letter (a Gazette

**Contradiction test** — built the vote-outcome contradiction (board

## DATA-INTEGRITY FAILURES

None of the automated-detection safety guarantees were actually violated —
no relationship, mention, or finding was ever auto-created without explicit
confirmation, at any point in this test. The identity-safety concern found
here (Bug #1) is a **UX/trust gap**, not a data-integrity failure: nothing
was silently written that a human didn't click to confirm. One structural
observation, not independently root-caused in this run: of the 5
intentionally-corrupted files, the ingestion batch reported only 3 as
"needing attention" (0 hard failures, 3 skipped), not the naively-expected
5 — plausibly explained by the zero-byte file legitimately producing empty
(not failed) extraction rather than a parse error, but this wasn't traced
further and is flagged here as an open question for a future, more targeted
test rather than asserted as a confirmed bug.

## UX FRICTION

- Single-option "Confirm as X" buttons carry no visual weight difference
  from a genuine strong match (Bug #1) — the single biggest trust-eroding
  friction point found.
- No way to tell, from the Review Queue itself, whether a document was
  scanned before or after the current entity roster was complete — an
  investigator has no way to know which already-reviewed documents are
  worth a second look after registering someone new.
- The audit trail is complete but unlabeled (see Three-Person Handoff) —
  every cross-reference is a manual lookup.
- "Mark irrelevant," listed in the original review-actions brief, does not
  exist as a distinct action anywhere in the UI.

## TOP 10 INVESTIGATOR PAIN POINTS

1. Typing a real question into Ask Sources returns nothing, with no
   indication why or what phrasing would work instead.
2. A single "Confirm as Raymond Payne" button looks exactly as trustworthy
   whether it's a rock-solid match or an unregistered stranger's document.
3. Discovering a second same-surname person mid-case means manually
   remembering which already-reviewed documents to go re-open — there's no
   rescan and no flag marking them stale.
4. Turning "Raymond Payne is on this board" into a queryable
   organization/government-body link takes several manual steps every time.
5. The review-history log requires opening a second tab to decode what any
   entry actually refers to.
6. "What's left to review" has no single answer — it's assembled from
   several separate filtered views.
7. No way to mark a document "not relevant" distinct from simply not acting
   on it.
8. A claim's supporting/contradicting search has to be done manually via
   keyword guesswork, since the natural question form returns nothing.
9. No visible signal distinguishing a document scanned with a complete vs.
   incomplete entity roster.
10. The Ask Sources answer for a genuinely-absent reference ("Ordinance
    2026-29") and a genuinely-present one ("Raymond Payne") look identical —
    both say "no matches," so a real negative is indistinguishable from a
    tool failure.

## TOP 10 CAPABILITY GAPS

1. Natural-language search (Ask Sources) — Bug #3, the single largest gap.
2. No confidence/strength signal on review-queue candidates.
3. No re-scan mechanism for already-ingested documents.
4. No automatic org/government-body suggestion from a confirmed mention.
5. No "mark irrelevant" action.
6. No single gap-awareness / investigation-health view.
7. No human-readable labels in the review-history audit log.
8. No per-document "scanned against N of M known entities" freshness
   marker.
9. Cross-filename duplicate detection is untested by the corpus itself (a
   corpus limitation, not a Chronium gap — noted above).
10. Multi-contradiction claim workflows (beyond one) weren't deep-tested
    this round — worth a dedicated follow-up.

## RECOMMENDED PHASE 5

**Immediate hotfix, before any phase work (not itself "Phase 5"):** fix
`extractSearchTerms()`'s incomplete stopword handling and/or
`searchInvestigation()`'s all-terms-must-match logic (Bug #3). This is
small, surgical, and blocking — Ask Sources is the product's front door and
it currently fails on ordinary investigator language.

**Recommended Phase 5: Identity Resolution hardening**, ahead of Timeline,
Source Tiers, and Network View, targeting Bug #1 and Bug #2 directly:
surface a visible confidence/strength distinction on review-queue
candidates (a bare-surname single-option match should not look identical to
a verified strong match), and build a real re-scan path — ideally automatic
on new-entity registration, at minimum a manual "re-scan this record"/
"re-scan all" action, made idempotent (replacing stale candidate rows
instead of duplicating them, closing Bug #2 at the same time).

## WHY THAT PHASE SHOULD COME BEFORE THE OTHERS

- **vs. Timeline**: genuinely tempting — "what changed before and after
  this vote" is a real, well-supported question this corpus could answer
  well with a timeline view, and nothing in this test argues against
  building one eventually. But Timeline is an *enrichment* layer sitting on
  top of an evidence graph that is assumed correct. Identity Resolution's
  gap is upstream of that assumption: this test found the exact mechanism
  by which the graph itself could be built wrong today, contained only by
  a disciplined tester reading every snippet — a real three-person team
  under deadline pressure is exactly the scenario least likely to have that
  discipline consistently. Fix the foundation before building a richer view
  on top of it.
- **vs. Source Tiers**: nothing in this test surfaced evidence that source
  reliability classification is an active pain point today; it's a
  reasonable future ask, not an urgent one.
- **vs. Network View**: the co-occurrence guarantees already work correctly
  (verified again this test); a network view would help *visualize*
  relationships that already exist, but this test's real finding was that
  *creating* those relationships is the actual manual bottleneck (cross-
  document test: 3 manual steps just to link one person to one
  organization). A view doesn't fix a creation-cost problem.
- **vs. "Questions/Searches Performed"** (i.e., iterating on the already-
  shipped Ask Sources feature as its own initiative): this is effectively
  covered by the immediate hotfix above, which is scoped much smaller than
  a full phase — once search actually matches natural language, no further
  phase-sized work is obviously indicated by this test's results.

If a future rerun of this exact benchmark shows the identity-safety
false-positive risk (Bug #1) has dropped to zero and the money-trail/
Ask-Sources recall numbers above have held or improved, Timeline becomes the
clear next candidate — this recommendation is a snapshot of what this
corpus found today, not a fixed roadmap ordering.

## GO / CONDITIONAL GO / NO-GO

**CONDITIONAL GO** for using Chronium today on a real Copperas Cove
investigation, conditional on the investigation team being explicitly
briefed on both HIGH-severity gaps until they're fixed:

1. Use short keyword phrases in Ask Sources, never full questions, until
   Bug #3 is fixed.
2. Treat every single-option "Confirm as X" candidate with the same
   scrutiny as an AMBIGUOUS one — always read the snippet, never trust the
   button alone — until Bug #1 is fixed, and re-open already-reviewed
   documents by hand whenever a new same-surname person is discovered
   mid-case, until Bug #2 is fixed.

With those two workarounds understood by the team, the rest of this test's
findings — fast bulk ingestion, correct dedupe, genuinely fast triage, real
contradiction preservation, zero auto-fabricated relationships/findings
anywhere in 12 test categories — support real, current use. Without that
briefing, a rushed or new team member would likely hit both HIGH-severity
gaps within the first working session.

## Bugs found (not fixed, per instruction)

### Bug #1 — HIGH — Bare-surname candidates offer false confidence with an incomplete entity roster

**Reproduction**: register only "Raymond Payne" as an entity. Bulk-ingest a
document containing bare "Payne" in an unrelated context (e.g., a Code
Compliance notice). Open it in the Review Queue.

**Expected**: a bare surname match should read as provisional/low-confidence
while the investigation's entity roster is incomplete, or the tool should
otherwise make it visually obvious this offer depends on no other
same-surname person being registered yet.

**Actual**: the candidate renders identically to a genuine strong match —
one enabled "Confirm as Raymond Payne" button, state UNREVIEWED — with no
signal that this is a weak, context-free surname match riding on an
incomplete roster.

**Investigator impact**: a rushed reviewer who trusts the single-option UI
rather than reading the full snippet would silently misattribute documents
to the wrong person. This is exactly the Marc/Raymond Payne failure mode
the project is named after — contained in this test only by investigator
discipline, not by the system. **Confirmed via Phase B of this same test**
that the underlying detection algorithm is fully correct once BOTH people
are registered (6/6 exact match against the corpus's designed ambiguous
set) — the gap is entirely about the incomplete-roster window, which is the
normal starting state of a real case.

### Bug #2 — MEDIUM — No re-scan mechanism; underlying scan function is not idempotent

**Reproduction**: register entity A, ingest documents, register entity B,
look for any "re-scan" action anywhere in the Review Queue.

**Expected**: either an automatic re-scan when a new entity is registered,
or an explicit manual "re-scan" action — and calling it twice on the same
record should not duplicate rows.

**Actual**: no re-scan control exists anywhere in the UI. Calling the
underlying `scanRecordForReview()` function directly (as this test did, to
measure the algorithm's correctness in isolation) adds a second, additive
set of candidate rows for the same passage rather than replacing the stale
ones.

**Investigator impact**: an investigation that discovers new people over
time — the normal case, not an edge case — accumulates permanently-stale,
overconfident candidate rows on already-reviewed documents unless someone
manually re-ingests everything, which is not a realistic workflow for a
live case.

### Bug #3 — HIGH — Ask Sources fails on virtually all natural-language questions

**Reproduction**: with Raymond Payne genuinely mentioned in multiple
ingested, confirmed documents, ask "Show me every record mentioning Raymond
Payne." via Ask Sources.

**Expected**: the real, present mentions of Raymond Payne should surface —
the same way the short query "Raymond Payne" already reliably does (verified
working, 8–9 results, across every short-phrase query run in this test).

**Actual**: `extractSearchTerms()` (`public/askCommands.js`) leaves "every"
and "mentioning" in the extracted term list — "every" isn't a stopword at
all, and only the inflections "mention/mentions/mentioned" are stopworded,
not "mentioning." `searchInvestigation()` (`public/db.js`) then requires
**every** extracted term to literally appear in a document
(`terms.every((term) => haystack.includes(term))`). No real document
contains the literal word "every" or "mentioning," so the AND-match fails
and zero results are returned — even though "raymond" and "payne" are both
present and would have matched alone. Reproduced identically for all 12 of
this test's questions (all in full-sentence/question form): genuinely
resolved, not a timeout (verified via a 60-second diagnostic ceiling, 0
timeouts recorded), consistently zero results.

**Investigator impact**: the single largest finding of this entire test.
Ask Sources is Chronium's primary conversational entry point, and it cannot
answer any of the natural, full-sentence questions a real investigator
would actually type — it only works if the investigator already knows to
type bare keyword phrases instead, which is not how the feature is marketed
or how any of this test's (or the brief's own) example questions are
phrased.
