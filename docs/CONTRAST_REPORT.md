# Non-text contrast report (WCAG 2.2 SC 1.4.11)

Generated by `node scripts/test-contrast.mjs --report=...` on 2026-10-22 (Chrome for Testing 152, Windows 11). The test fails if any essential boundary is below 3:1.

## What counts as essential

A boundary is held to 3:1 when it is the thing that identifies a control, or carries meaning the text does not:

| Held to 3:1 | Why |
|---|---|
| Text inputs, search boxes, selects, textareas | The border is what shows where to type |
| Secondary buttons, chip buttons, small action buttons | Border/shape identifies a button |
| The drop zone (dashed border) | Marks the drop target |
| Checkboxes and radio buttons | Browser-drawn control outline |
| Focus ring and selected-tab underline | Show where you are |
| Missing / Not reviewed yet / Unresolved left edges | Supplement the text tags |

**Not held to 3:1 (decorative, the text carries the meaning):** card, panel, dialog and table borders, row dividers, the borders on text tags and status badges (each has a text label), quote bars, disclosure boxes. Disabled controls are exempt (SC 1.4.11 does not apply to inactive components).

## Change made

A new token `--control-border` (website) / `--control` (extension) for control boundaries, applied to the controls above. The old `--border` / `--line` stay for decorative lines.

| Token | Dark | Light |
|---|---|---|
| decorative border (unchanged) | `#292e34` / `#2a3036` | `#b8b3a4` |
| control border (new) | `#7a828b` | `#6b675c` |

Also: `accent-color` on checkboxes/radios, a stronger hover border on buttons, `prefers-contrast: more` raises dividers and secondary text, forced-colors keeps only the selected tab underlined (system `Highlight`), and the extension's light-theme Unresolved edge was darkened (3.06:1 to above 4.5:1).

## Method

Three layers, each in dark and light, website and extension:
- **token**: the colours from the live CSS custom properties against each surface they can sit on;
- **pixel**: real controls (text input, select, textarea, checkbox, radio, secondary button, search box; in the extension text input, search input, button) rendered on the page background, surface and raised surface, screenshotted, and the boundary pixel compared with the pixel just outside it. This measures what a user sees, including browser-drawn checkboxes and radios;
- **real**: every essential control on the real pages (each workspace tab, home with results, the extension's tabs and case views), border colour against the colour behind it.

## Result

(The "before" run used the first version of this tool, which audited fewer real-page routes; its token and pixel measurements are directly comparable.) Before the change: 112 measurements, 84 below 3:1. After: 132 measurements, 0 below 3:1.

## Limits of this measurement

- It measures colour contrast of boundaries. It does not judge whether a boundary is *necessary* for a particular control; that decision is the table above.
- Controls that only exist after specific interactions (for example the evidence picker in the claim form, the file preview button) were not rendered on a real page here; they use the same token as the measured ones.
- Browser-drawn parts (checkbox/radio rings, the file-chooser button, select arrows) depend on the browser and operating system; only Chrome 152 on Windows was measured.
- Windows High Contrast / forced-colors is checked separately in `scripts/test-a11y-modes.mjs`, because colours are replaced by system colours there.
- This is not a conformance statement.
